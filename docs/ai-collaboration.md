# AI 协作过程

依据是 `docs/dev-log.md` 和 `git log`。指令只摘日志里的摘要，不补对话原文。

## 链路

| 环节 | 我做什么 | AI 做什么 |
| --- | --- | --- |
| 需求 | 划定这一刀的验收：函数契约、测试场景或真实闭环。不把下一阶段的写入、评测提前塞进来 | 不改需求范围 |
| 上下文选择 | 只给这一刀用到的契约和接口。M0 给了 `docs/tools.md` 与 `docs/data_model.md`，没有塞需求和验收全文 | 在给定材料里实现，不另找一套规则 |
| 指令 | 写明可改文件、禁止项、必须跑的命令。例如只新建 `policy.py`、只改 `validation.py` 的常量来源 | 按文件清单改，不顺手改测试预期或判定顺序 |
| 方案审查 | 先看结构和判定顺序，再决定接受或收紧。空白身份返回 OK 被拒绝 | 给出实现；不自行放宽契约 |
| 实现 | 拆步：先契约，再存储，再工具，再循环，再提交 | 在当前一步里写代码和测试 |
| diff 审查 | 对照契约看返回形状、错误码和有没有多写文件 | 按审查意见改指定位置 |
| 独立测试 | 在项目根运行 `python3 -m unittest discover -s tests -t .`，保留真实输出。直接执行测试文件不算 | 把命令输出交出来，不把未运行写成通过 |
| 纠偏 | 记录偏差归属，补用例或改提示词后再跑。代码通过之后还有可辩护性门 | 按纠正后的预期改，不改测试来迁就错误实现 |

## 我的规则

下面每条都能在开发日志里找到对应做法。

1. **先契约，后代码。** M0 按 `docs/tools.md` 实现校验。M2 的指令是先设计文档，再拆成存储写层和接线。
2. **一次只推进一步。** 存储阶段明确不实现写接口。`policy.py` 那次只搬窗口天数，不动判定顺序、测试和文档。
3. **未运行不算通过。** M0 要求贴出实际输出并说明 5 是测试方法数；确认有效期那条在测试跑完后才回填 Ran 101 tests OK，不留占位。
4. **不许用实现改契约或测试预期。** M0 指令写了这一点。C03/C04 后来改的是评测期望，因为原期望把更安全的路径判失败，并记在 `docs/evaluation.md`。
5. **偏差要留下归属，不能只留下最终代码。** 空白身份、preview 注入 `owner_id`、M2 的六处设计问题，都写在「发现的偏差」。
6. **没做的能力写在局限里。** 只读工具阶段写明 preview、submit 和模型可见 schema 都还没有。可辩护性门的结论是：代码正确不等于会讲。

## 例子

### 例 1 · 空白身份（`3c6b745`）

- 指令片段：只实现 `validate_return_request` 与测试；不许改契约或测试预期来迁就实现。
- AI 产出：`return_agent/validation.py` 和 `tests/test_validate_return_request.py`。
- 发现的问题：空白身份返回 OK。日志把这判为危险，并补了顺序用例 T37：对调第 3、4 步时原用例仍全绿。
- 修正：第 1 步改为空白身份返回 `INVALID_INPUT`，同步契约，加 T38。
- 结果：`3c6b745`。日志记录 `Ran 5 tests` / `OK`，并说明 5 是方法数、用例是 38。

### 例 2 · 真实回复对不上 trace（`5fd34c2`）

- 指令片段：接真实模型，跑通澄清、预览、拒绝；循环测试用假 LLM，不联网。
- AI 产出：`llm.py`、`agent.py`、`trace.py`、`tool_schemas.py`、`cli.py`。
- 发现的问题：回复出现不存在的官方客服和 App；「订单 1001」被说成「订单10」。当时的 trace 没有 user / assistant，无法把原句和回复对在一起。
- 修正：提示词禁止编造渠道，并要求订单号与工具返回值精确匹配；trace 增加这两类事件。
- 结果：`5fd34c2`。日志记录 `Ran 51 tests` / `OK`，以及 `docs/traces/20261019-1625*.jsonl` 三次运行不再出现「订单10」。

### 例 3 · 提交前的六处设计问题（`97dd3b8`、`1b5daaf`、`95c73c0`）

- 指令片段：先写文档再实现；拆成 M2a 写层和 M2b 接线；submit 的检查和写入放在同一个 `BEGIN IMMEDIATE` 事务里。
- AI 产出：存储写层、`submit_return_request`、确认接线。
- 发现的问题：日志列了六条。嵌套 plan 对扁平列、确认外键、隐式事务、旧库版本、状态变化先触发 `PLAN_CHANGED`、submit 错误表多写了 `STORE_UNAVAILABLE`。
- 修正：`97dd3b8` 组装契约形状、加外键、拒绝隐式事务和旧库。`1b5daaf` 改错误表，并把重新校验写成防御性分支，用单独测试覆盖。
- 结果：`95c73c0`。日志记录 `Ran 93 tests` / `OK`，端到端 trace `docs/traces/20261019-192522-83529d.jsonl` 新增申请 9003。

### 例 4 · 评测期望和提示词（`af16df5`）

- 指令片段：评测报告第 5 节记录的是跑完之后的改法，不是事先把 30/30 写进验收。
- AI 产出：`eval/` 案例、固定流程基线，以及加强后的提示词。
- 发现的问题：首次全量 6/10。C03/C04 要求 preview，Agent 查询后找不到；C08/C09 自行判断数量。第三次全量又有一次 C08 绕过 preview。
- 修正：C03/C04 改为只要求 `query_orders`。提示词要求任何数量判断都先调用 preview，包括 0、负数和超量。
- 结果：`af16df5` 的 `docs/evaluation.md`：Agent 30/30，基线 9/10。基线失败的 C02 记为结构性失败，没有改成通过。
