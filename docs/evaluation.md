# 评测报告（M3）

## 1. 设置

- 日期：2026-10-19
- 模型：DeepSeek `deepseek-chat`（OpenAI 兼容端点）
- 代码：M3 工作区（提交号 af16df5）
- 数据：`return_agent/data/demo.db` 的种子数据（7 条订单行、2 条历史申请），每个案例使用独立临时库
- 案例：10 个固定案例（`eval/cases.py`），覆盖允许、澄清、越权、不存在、过期、未妥投、不可退、数量非法、数量不足、确认提交

## 2. 方法

- 每个案例运行 3 次；每次从全新种子库开始。
- 成功判定不使用人工或 LLM 打分，只看结构化信号：
  1. 必需工具是否出现、参数是否匹配；
  2. 工具返回的 `code` 是否出现；
  3. `submit` 是否被调用；
  4. 最终回复的少量关键词（contains / not_contains）；
  5. `return_requests` 的新增条数。
- 基线为固定流程（正则解析订单号/数量 → 直接调用 preview），不使用模型。
运行方式：

    python -m eval.run_eval
    python -m eval.run_eval --baseline

`--baseline` 使用 `eval/baseline_fixed.py` 的固定流程，不调用模型；token 与延迟记为 0。

## 5. 迭代过程（如实记录）

1. 首次全量：6/10。两个原因：C03/C04 期望 preview（但 agent 走"查询后找不到"路径，更安全）；C08/C09 绕过 preview 自行判断数量。
2. 修正：C03/C04 改用例；C08/C09 改 prompt + 工具描述。第二次全量 10/10。
3. 第三次全量 9/10：C08 再次绕过 preview（同一输入上轮通过），暴露模型随机性。
4. 加强 prompt（明确 0/负数/超量也必须调用 preview），连续 3 次 10/10。

## 6. 失败分析

- 基线 C02：结构性失败。正则无法把"蓝色的短袖"映射到"蓝色 T 恤"，也无法在没有订单号时主动查询。这是固定流程的固有边界。
- Agent C08（历史）：答案正确但流程错误——自行判断"0 件不行"，没有调用 preview。属于"过程合规"问题，不能只看最终答案。

## 7. 局限

- 每个案例仅 3 次，样本小；模型输出有方差。
- 只有一个模型、一套种子数据。
- 关键词判定是启发式的，可能漏判措辞差异。
- 未做人工评估，也未覆盖多轮长对话与上下文压缩。
- 基线为作者手写的固定流程，不代表所有非 Agent 方案。

## 8. 结论

- 10 个固定案例上，Agent 30/30，基线 9/10。
- 基线在结构化输入下零成本、确定性高；在非结构化输入（C02）上结构性失败。
- Agent 每案约 3.7k token、2.6 秒；主要成本来自多轮工具调用（C10 最高，约 7.5k token）。
- 结论：输入能否被规则稳定解析，是选择固定流程还是 Agent 的关键判据；不是"Agent 一定更好"。
